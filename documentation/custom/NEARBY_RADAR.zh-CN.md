# 附近设备雷达

两个独立入口：`Apps → Bluetooth → BLE Radar`（文件 `nearby_radar.fap`）和 `Apps → WiFi → WiFi Radar`（文件 `wifi_radar.fap`）。**蓝牙版使用 Flipper 自带的 STM32WB55，无需 ESP32；Wi-Fi 版通过 ESP32 扫描接入点。** 两版均先显示设备列表，再选名字进入目标信号页。官方手机 App 可通过屏幕遥控操作；这不是手机独立扫描器。

## 找设备

1. 蓝牙版启动后自动在本机被动扫描，不占用 GPIO/UART，不修改蓝牙开关、配对记录或发射功率。需安装本分支完整固件包中的 **Full 1.20.0 无线栈**；仅复制 FAP 到使用 Light 栈的其他固件会显示 `Full BLE stack required`。
2. Wi-Fi 版仍需 ESP32 运行本仓库 `companion/nearby_radar` 的 NR1 配套程序，使用已确认的 UART 接线与供电。启动时自动使用 Momentum 的 ESP UART 设置、115200 波特率；握手及 RUN 确认后开始扫描。没有板卡显示 `Waiting for ESP32` / `No ESP32 response`，长按右键切换 USART/LPUART，串口忙时按 OK 重试。不会填入演示设备。
3. 列表显示扫描到的名称，按信号从强到弱排列。最上面是接收信号最强的观察，**不能保证物理距离最近**；没有名称时显示 BLE / WiFi 加地址尾号，避免多个无名设备无法区分。上下选名字，按 OK 打开目标雷达页。
4. 长按 OK 输入名称或地址片段，忽略英文字母大小写。蓝牙版在观察入库前过滤；Wi-Fi 版还把条件发给配套板，避免无关观察占满列表。更改条件会清空旧列表并重新收集；清空搜索框可恢复全部。
5. 雷达页只保留设备名、两个圆环、平滑后的 RSSI 和 Stronger/Weaker/Steady。走动时比较趋势；按 OK 查看地址、无线类型、Wi-Fi 信道及最后观察时间，按 Back 返回雷达。圆点位置只表达相对信号强弱，**没有方位和米数含义**。
6. 超过 12 秒没有观察到目标，圆点隐藏、读数变成 `-- dBm` 并显示 Lost signal；列表中超过 60 秒未出现的观察不再列出。左键暂停/恢复扫描；目标页按 Back 返回列表，列表再按 Back 退出并停止该扫描会话。

本机键盘输入英文及数字；中文 SSID 可从列表选中，显示受设备现有字库限制，也可按地址片段筛选。名称来自设备主动广播的数据，可能为空、重复或变化。BLE 私有地址变化后作为新观察处理，不推断它和旧地址属于同一设备。

## 能发现什么

- BLE：本机接收传统 BLE 广播，名称取自广播中的完整/缩短名称字段。100 ms 扫描间隔、60 ms 接收窗口；保留重复报告以持续更新 RSSI。不开启主动扫描请求、不向目标建立 GATT 连接。只在扫描响应中提供名称的设备可能无名；不覆盖经典蓝牙或仅扩展广播的设备，也不保证每个耳机、手机都可见。
- Wi-Fi：参考 ESP32 支持的 2.4 GHz 接入点，显示 SSID/BSSID、信道与接收信号。扫描列表不是路由器的已连接客户端清单，也不证明某个设备是摄像机。
- 最多保留 32 条观察，名称上限 32 字节，HCI/广播字段、UART 行和队列均有界。满表时优先淘汰过时记录，或让明显更强的信号替换最弱记录；选中的目标不会被替换。BLE 公有/随机地址分别记录；损坏数据不会当成设备。

## 本机蓝牙与固件空间

**首次从旧 Light 固件迁移时，必须分两步安装。** 先安装与目标完整包对应的 `bootstrap` 主固件包（只更新主固件，保留现有无线栈），确认新主固件能启动，再安装对应的完整 `update` 包来切换 Full 栈并更新全部资源。引导阶段只是临时步骤，在完整资源安装完成前不要打开文件管理器或把它当成安装成功。

原因是升级器会先写无线栈、再写主固件，切换无线栈期间需要多次重启。旧主固件若超过新 Full 栈起始地址 `0x080CE000`，单次直接升级可能覆盖旧主固件的启动依赖。只验证“新主固件与新无线栈不重叠”不足以验证迁移过程。构建检查现在会另外生成只含 `firmware.dfu`、`updater.bin` 和部分更新清单的 `bootstrap` 包，不包含无线栈、资源或 option bytes 写入。

在构建目录可用 `python scripts/prepare_native_ble_bootstrap.py --package <完整包.tgz> --output <新bootstrap包.tgz> --installed-dfu <与设备当前版本一致的旧firmware.dfu>` 生成并检查；最后一项用于检测旧主固件是否覆盖新栈范围，不会读取或烧写设备。无法确认当前主固件大小时，同样先完成引导阶段。本步骤不替代设置备份与安装后的逐项验收。

本分支从 Light 切换到仓库固定的 ST Full 1.20.0 无线栈（起始地址 `0x080CE000`），初始化 GAP 时保留 peripheral 角色并增加 observer 角色。观察过程与已有手机服务共用无线栈，不重置服务、清除密钥或断开手机以开始扫描。退出同步撤销回调后再释放应用队列；扫描停止的完成事件到达前，不启动重叠过程。

主固件采用链接时体积优化，外部 FAP 保持普通可重定位编译。启动、上下文切换及崩溃寄存器捕获的汇编保留原编译方式。链接阶段按实际无线栈边界限制 Flash，并检查启动向量；更新包还会复核固件与无线栈是否重叠，不能跳过保护强行烧录。

文件管理器界面改为按需加载 `/ext/apps_data/archive/plugins/archive_ui.fal`，保留现有桌面快捷键、原目录上下文、收藏与文件关联操作；默认快捷键是短按下键，用户自定义按键不变。共享收藏 API 仍在主固件。该界面需要 SD 卡及匹配的资源模块，模块缺失或不兼容会显示重装资源提示。安装时必须同时更新完整资源，不能只刷主固件或只替换雷达 FAP。

信号受天线朝向、遮挡和反射影响；Stronger 只表示接收信号增强，不保证实际距离缩短。

## 配套板与构建

`companion/nearby_radar/platformio.ini` 固定 PlatformIO espressif32 6.10.0，为普通 ESP32 开发板提供可编译的参考环境。里面的 UART RX/TX 是参考配置，**不是已验证的 AIO Board 1.4 接线**。实际板卡芯片、UART 引脚及供电须在实物接入后确认；不能按三合一板名称直接刷写。

参考环境为 4 MB Flash，使用框架自带的 `huge_app.csv` 分区（3 MB 应用、无 OTA 双分区），以容纳 Wi-Fi 与 BLE 协议栈。不同容量的实际板卡需要相应分区配置。本应用不自动开启 Flipper 的 5V 输出，实际供电按已确认的板卡规范处理。

已有 Marauder/Ghost ESP 等固件不实现 NR1 协议。参考程序是独立固件，刷入会替换 ESP32 原程序；本轮未执行板卡刷写。后续应先识别现有固件，再决定适配现有输出或使用参考程序。

参考程序只被动接收 BLE 广播、被动扫描 Wi-Fi 接入点，不连接接入点、不广播模拟外围设备、不控制被观察设备。Flipper 定期发送存活消息；10 秒没有收到有效控制消息时配套板停止扫描。BLE 扫描分片最长约 2 秒，停止命令可能等待当前分片完成。

## 串口协议 NR1

所有帧为 ASCII，LF 结尾，CR 可忽略。设备名称以原始字节的大写十六进制表示，避免逗号和控制字符破坏帧边界。

- 控制：`NR1,HELLO`、`NR1,PING`、`NR1,SCAN,A`（全部）、`NR1,SCAN,B`（BLE）、`NR1,SCAN,W`（Wi-Fi）、`NR1,STOP`。
- 名称/地址筛选：`NR1,FILTER,<名称片段的十六进制>`，空字段清除筛选。
- 握手：`NR1,R,ESP32,BW`；状态：`NR1,S,RUN` 或 `NR1,S,STOP`。
- 观察：`NR1,D,<B或W>,<12位十六进制地址>,<RSSI>,<信道>,<名称十六进制>`。BLE 的信道字段为 0；RSSI 必须为 -127 到 -1。

## 验证边界

自动测试编译实际 HCI 报告解析器、广播名称提取器、`radar_core.c` 及扫描状态函数，检查多报告和截断数据、名称优先级、公有/随机地址隔离、筛选、信号趋势、超时、密集环境容量、目标保留、扫描所有权及停止后的回调生命周期。两份清单的实际编译参数也用于验证后端隔离：BLE 版调用本机扫描 API，只有 Wi-Fi 版发送 `NR1,SCAN,W`。

此前 ESP32 双后端版本的安装记录见 [存储及雷达记录](STORAGE_RADAR_20261023.md)；该记录不能作为本机 BLE 扫描的验收证据。本机版的最终构建和 USB/无线验收需单独记录。

用户确认 AIO 板当前未连接，因此 Wi-Fi 实际扫描、板卡固件和 UART 引脚仍需实物验收。电脑 BLE/GATT 测试不能替代 iPhone 官方 App 的真机验收。
